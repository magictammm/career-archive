# 02 · 三段式深挖

## 结构

一段经历下的每个项目一份 md，固定三段：

```
# 项目深挖-NN · 项目名

> 一句话定位：这是什么产品 / 什么项目，为谁解决什么问题。

## 一、项目背景
## 二、产品介绍
## 三、我的角色 · 解决的问题 · 结果反馈
```

篇幅配比：一 ≈ 20%，二 ≈ 25%，三 ≈ 55%。第三段写不长，说明素材还不够。

## 一、项目背景

回答「为什么做这个项目」。至少覆盖四项中的三项：

- **市场**：规模、增速、价格带分布、空白点（带数字和年份）。
- **用户**：目标用户是谁、核心场景、现有方案哪里不够用。
- **竞争**：头部是谁、同类是谁、差异化机会在哪。
- **内部动因**：产品线补位、平台换代、客户定制、战略试水。

写法要求：
- 数字要带口径（年份、单位、来源类型），不写裸数字。
- 一段一句判断，不要罗列式堆砌。
- 用户访谈、电商评论、竞品拆解这类调研动作写清方法与样本量。

## 二、产品介绍

- **市场定位**：价格档、对标谁、靠什么打。
- **用户定位**：谁买、什么场景、替代方案是什么。
- **解决的痛点**：不写功能清单，写「原来怎么办 → 现在怎么办」。
- **关键规格**：主控 / 系统 / 关键器件 / 核心能力，只写能支撑判断的那几个。

## 三、我的角色 · 解决的问题 · 结果反馈

这是简历、面试、述职真正取用的部分，按四个小节展开：

### 3.1 我的角色
- 角色名 + 边界：负责哪条线（需求 / 方案 / 推进 / 供应链协同），谁不归我管。
- 团队规模与协作面：直接带几人、跨几个部门、对接几个供应商。
- 如果中途角色变化（接手、扩权、转岗），写清时间点与原因。

### 3.2 遇到的问题
每个问题写成「现象 → 为什么难 → 约束是什么」三段。

难点要落在真实约束上：成本、周期、芯片能力、供应链、跨部门资源、组织决策。避免写成「沟通不畅」「需求变更」这类空泛归因。

### 3.3 我的判断与取舍
- 我主张什么，依据是什么。
- 什么方案被否掉了，否决理由是哪条硬约束。
- 有没有主动做减法（砍功能、砍形态、换平台），代价与收益各是什么。
- 阶段演进类项目（方案改了几版）用表格写：阶段 / 时间 / 方案 / 结论，再补一张「上一版难点 → 这一版怎么解」对照表。

### 3.4 结果与反馈
优先级从高到低：
1. 量化业务结果：上市时间、周期偏差率、成本、评分、销量、转化。
2. 量化交付结果：需求包闭环度、延期天数、缺陷数、评审通过率。
3. 状态结果：EVT / DVT / 量产 / 未上市，写清卡在哪。
4. 组织反馈：评奖、晋升、复用推广（其他项目借用我的方案/SOP）。

延期或失败必须归因到具体环节，并说明该环节是否在我的责任线内。**不揽责也不推责**，这是可信度的来源。

## 正反例

| 弱写法 | 强写法 |
| - | - |
| 负责 C4502 项目的需求工作 | 独立负责 C4502 全部软件需求线：208 天计划期内输出 ES/DVT 两版需求包，跨 25 个专业领域对齐 80+ 人 |
| 遇到供应链问题导致延期 | 延期 62 天（29.8%），主因是镜头模组分批交付 + 开模散热 fail + 声学气密性报废，三处均在硬件线；软件需求包按原计划提前闭环 |
| 优化了传输延时 | 上代图传延时 5–6 帧，主导链路重构后压到 2 帧以内，端到端延时降 60%+ |
| 参与多个阶段方案讨论 | 主导三版硬件方案收敛：一拖二带屏（成本超 PRD 30%）→ 一拖一（芯片 GUI 不支持）→ 轻双摄无屏（立项通过） |

## 常见坑

- **写成 JD**：全是「负责 / 参与 / 配合」，没有判断和结果。第三段必须是「我决定了什么」。
- **只写成功**：被否掉的方案、失败的阶段才是差异化素材，别删。
- **量化造假或含糊**：拿不到精确值就写区间或状态，不要编。
- **一份文档塞多个项目**：弹层会混，检索会乱。一个项目一份。
- **忽略反馈闭环**：上市反馈、用户评价、内部复用，这些比自评有说服力。
