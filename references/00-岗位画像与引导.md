# 00 · 岗位画像与引导

> 目的：让**任何岗位**的人都能走同一套流程，产出同一种白皮书。
> 岗位不同，改的是「纵轴用什么分层 / 抓哪些量化指标 / 深挖重点 / 章节权重」，不改流程。

---

## 为什么必须先问

同一个问题「你做过什么项目」，三种岗位要三种问法：

| 岗位 | 「项目」长什么样 | 量化证据 |
| - | - | - |
| 硬件产品经理 | 机型 / 型号 / 价位带 | 立项数、上市节点、BOM 目标、销量 |
| 软件产品经理 | 模块 / 版本 / 平台 | DAU、转化率、留存、需求吞吐 |
| 业务分析 BA | 需求线 / 系统 / 交付批次 | 需求条目数、返工率、PI 交付准时率 |
| 研发工程师 | 系统 / 服务 / 迭代 | QPS、P99、故障率、代码覆盖率 |
| 运营 / 增长 | 活动 / 渠道 / 内容矩阵 | ROI、CAC、GMV、涨粉、复购 |
| 销售 / BD | 客户 / 行业 / 大单 | 回款额、签单率、客户数、周期 |

**若不先问，就会用「硬件 PM 的价格轴」去套一个运营岗，纵轴全是空的。**

---

## 第 1 轮 · 六个必问（一次问完，别拆成十几轮）

直接照抄下面这段发给用户，括号里是示例，让他照着改：

```
为了把档案搭成能直接用的样子，先确认 6 件事（一次答完即可，不确定的写「不确定」）：

1. 目标岗位：现在做什么岗？下次想投什么岗？（例：软件产品经理 → 硬件产品经理）
2. 行业与业务：什么行业、卖给谁？（例：智能影像设备，B2C 出海 + B2B 渠道）
3. 公司体量与位置：公司多少人、你所在部门几个人、向谁汇报？
4. 你交付的东西：代码 / 需求文档 / 设计稿 / 内容 / 客户 / 合同 / 报表？（可多选）
5. 协作半径：带不带人？跨几个部门？对接外部供应商吗？
6. 这份档案先解决什么：求职 / 晋升答辩 / 述职 / 年度复盘 / 纯归档？
```

**每个答案改变什么：**

| 问题 | 影响 |
| - | - |
| Q1 目标岗位 | 决定岗位族 → 纵轴与指标（见下表）；目标岗与现岗不同时，额外产「迁移叙事」章节 |
| Q2 行业业务 | 决定外部数据要不要抓（竞品、市场规模），决定 B2B/B2C 叙事口吻 |
| Q3 公司体量 | 决定「影响力」怎么算：大公司写模块与协同范围，小公司写从 0 到 1 与全链路 |
| Q4 交付物 | **最硬的判定信号**，用来定岗位族（见判定规则） |
| Q5 协作半径 | 决定「团队规模」维度与是否出现「带人 / 跨部门推动」类证据 |
| Q6 用途 | 决定章节权重：求职 → 项目深挖与 STAR 加重；述职 → 结果与复盘加重；纯归档 → 台账与证据加重 |

## 第 2 轮 · 岗位族画像（按 Q1 + Q4 落到其中一行）

| 族 | 识别信号 | 甘特纵轴（分层依据） | 必备量化指标 | 深挖第三段重点 | 白皮书加重章节 |
| - | - | - | - | - | - |
| 产品经理（软件 / SaaS） | 交付 PRD、版本、平台 | 模块 / 端（Web / App / 后台 / 开放平台） | DAU·MAU、转化率、留存、需求交付周期、版本数 | 需求取舍与优先级依据、跨端一致性、上线后数据 | 项目深挖、能力模型 |
| 产品经理（硬件 / 智能设备） | 交付机型、BOM、认证 | **价格带**（旗舰→入门） | 立项数、EVT/DVT/PVT 节点、目标成本达成、销量、返修率 | 规格取舍（成本 vs 体验）、供应链与认证卡点、软硬协同 | 项目深挖、硬件/软件双甘特 |
| 业务分析 BA / 需求分析 | 交付需求规格、规则表、验收标准 | 需求类型（资金 / 交易 / 内容 / 合规 / 平台） | 需求条目数、变更率、PI 准时交付率、缺陷回流数 | 把口语业务翻译成规则的证据、边界与例外处理 | 项目深挖、方法论 |
| 研发工程师 | 交付代码、服务、架构 | 系统分层（接入 / 服务 / 存储 / 端侧） | QPS、P99、可用性、故障数、发布频次、覆盖率 | 技术选型理由、性能瓶颈定位、故障复盘 | 能力模型、技术深度章 |
| 测试 / 质量 / SRE | 交付用例、质量报告、稳定性 | 质量活动（用例 / 自动化 / 灰度 / 监控） | 缺陷密度、逃逸率、自动化覆盖率、MTTR | 漏测归因、质量门禁设计 | 方法论、结果章 |
| 设计（UI/UX / 工业） | 交付设计稿、规范、模型 | 产品线 / 端 / 设计系统 | 交付稿数、走查通过率、可用性测试结论、组件复用率 | 设计决策与用户证据、与研发的折中 | 作品章（图为主） |
| 运营 / 增长 / 内容 | 交付活动、渠道、内容 | 渠道 / 活动类型 / 内容矩阵 | ROI、CAC、GMV、涨粉、复购、转化漏斗 | 投放与内容的因果链、可复用打法 | 数据章、方法论 |
| 市场 / 品牌 / PR | 交付 Campaign、内容、媒体 | 渠道 / 战役 / 区域 | 曝光、线索量、媒体覆盖、声量变化 | 预算分配逻辑、效果归因 | 案例章 |
| 销售 / BD / 客户成功 | 交付客户、合同、回款 | 客户行业 / 区域 / 客单价 | 回款额、签单率、客单价、续约率、周期 | 关键单的推进路径、丢单复盘 | 结果章、客户案例 |
| 项目管理 / PMO | 交付计划、里程碑、风险表 | 项目组合 / 阶段 | 准时率、预算偏差、风险关闭率、资源利用率 | 冲突调解、范围控制 | 方法论、治理章 |
| 职能（HR / 财务 / 法务） | 交付制度、报表、流程 | 职能模块 / 业务单元 | 招聘周期、成本节约、合规事件、流程时效 | 制度落地阻力与破解 | 流程章、结果章 |

**用法**：命中一行后，把该行的「纵轴」写进框架页 config 的分层字段，「必备量化指标」进阶段 3 台账，「深挖重点」进阶段 4 第 3 段写作提纲，「加重章节」进阶段 5 的章节权重。

## 第 3 轮 · 项目清单（分批要，不要一次要全部）

给用户这个表头，让他按公司逐段填，**一行一个项目，缺的留空**：

```
公司在职期间：____ 至 ____
| 项目/型号 | 一句话定位 | 我参与的起止 | 我的角色 | 关键数字（随便写，能想起几个写几个） |
```

规则：
- 用户只想起 3 个就先做 3 个，做完再问「还有吗」——比一次要 12 个更容易问全。
- 同一产品线的多代产品**分行**，不要写「XX 系列等」。
- 用户填不出「关键数字」时，追问这 4 个最小替代：**多久、几个人、多少钱、上线没有**。

## 判定规则（Q4 是硬信号）

```
Q4 含「代码 / 服务」        → 研发工程师族
Q4 含「需求 / 规则 / 验收」  → BA 族（若同时有 PRD 且定优先级 → 软件 PM 族）
Q4 含「设计稿 / 模型」      → 设计族
Q4 含「活动 / 内容 / 渠道」  → 运营或市场族（看是否背收入指标）
Q4 含「客户 / 合同 / 回款」  → 销售族
Q4 含「计划 / 里程碑」      → PMO 族
Q2 含「硬件 / 设备 / 制造」+ Q4 含 PRD → 硬件 PM 族
Q1 与 Q4 冲突时              → 以 Q4 为准（人会高报岗位，但交付物不会说谎）
```

跨族经历（例：BA → 硬件 PM）按**每段经历各自定族**，不强行统一；跨段迁移写成「能力迁移表」，这本身就是白皮书的高价值章节。

## 信息缺失时的降级策略

| 缺什么 | 怎么办 |
| - | - |
| 缺项目清单 | 先从旧简历 / 旧周报里抽一版草稿（标 L3），让用户勾选与纠正，不空白等他 |
| 缺量化 | 用状态词占位（已上线 / 通过评审 / 移交量产），并写入「待补清单」，禁止编数字 |
| 用户说不清岗位族 | 反问他最近一周实际在做什么、交付给谁验收，用产出物定族 |
| 只有一段经历 | 照常走全流程，白皮书「职业曲线」章改为「能力现状 + 下一步」 |
| 用户不愿提供薪资 | 薪资章整章隐藏，不外显占位符 |

## 开场话术（可直接用）

```
我可以把你这几年的经历整理成一份《个人职业档案白皮书》——
不是简历，是底档：每段经历有哪些项目、每个项目你具体做了什么、
最后连成职级/职责/复杂度/团队/影响力五条曲线，再配薪资变化。

流程分四步，你只需要配合前三步：
① 我问 6 个问题（岗位、行业、团队、交付物、协作半径、用途）
② 你给一份项目清单，想不起来的先空着
③ 我逐项目提 3-5 个追问，你口述即可，不用写文档
④ 我产出：单文件 HTML 白皮书（可点开每个项目看详情）+ 项目深挖文档 + 待补清单

先回答这 6 个问题（不确定的写「不确定」）：
...
```
